# telegram.service.go

Через этот сервис провайдер отвечает на спор по сделке, не заходя в админку. core публикует событие о споре, бот присылает в Telegram-группу провайдера карточку с двумя кнопками, а нажатие превращает в команду `Payments.Dispute.TGRespond` обратно в core. Вторая задача - пересылать операторам технические алерты `System.TechAlert` от других сервисов. Как споры устроены на стороне сделки - в [корневом README](../../README.md).

Цвета на схеме те же, что в корневом README: оранжевый - наши сервисы, синий - провайдер, серые плашки - хранилища. На схеме компонентов, по правилам C4, соседние сервисы тоже синие.

## Путь одного спора

Мерчант открыл спор по входящей сделке, которую отменили по TTL: он уверен, что плательщик заплатил. Причина спора - `PAYMENT_EXISTS`, у провайдера привязана Telegram-группа.

![core публикует Payments.Deal.Disputed, сервис проверяет поля и дубль в Redis, берёт ссылку на первое вложение у files.service.go, отправляет карточку в группу провайдера, ловит нажатие кнопки и проверяет чат, передаёт ответ в core и правит карточку; раз в 30 секунд сверяет открытые карточки со статусом сделки](docs/diagrams/dispute-flow.svg)

1. core рассылает событие `Payments.Deal.Disputed` через golang-cqrs с `Broadcast: true` (`core.service.go/internal/infrastructure/services/telegram/publisher.go`). Это обычное событие NATS, не JetStream. Поля в snake_case:

   ```json
   {
     "deal_id": "8d1f...",
     "provider_deal_id": "PRV-20931",
     "direction": "IN",
     "dispute_reason": "PAYMENT_EXISTS",
     "provider_tg_group_id": -1001234567890,
     "amount": "5000",
     "currency_code": "RUB",
     "requisite_issuer": "Сбербанк",
     "requisite_value": "2200 **** 1234",
     "attachment_keys": ["deals/8d1f.../receipt.jpg"]
   }
   ```

2. Сервис молча пропускает событие без `deal_id`, `dispute_reason` или `provider_tg_group_id` (`entity/dispute.go`). Потом смотрит в Redis: если по сделке уже висит карточка без ответа, новую не шлёт. Карточка с ответом не мешает: значит, по сделке открыли новый спор.
3. Сервис идёт по `attachment_keys` по порядку и запрашивает `Files.GetURL`, пока не получит presigned-ссылку на S3. Вложение в карточке одно: Telegram не прикрепляет inline-кнопки к альбому.
4. Карточка уходит в группу: с картинкой - через `sendPhoto`, с другим файлом - через `sendDocument`, без вложения - через `sendMessage`. Если Telegram не смог скачать файл, карточка уходит через `sendMessage` с пометкой, что вложение не загрузилось: без карточки провайдер не увидит спор вовсе. Все поля события, которые попадают в текст, экранируются под HTML-разметку Telegram. Под текстом две кнопки с `callback_data` вида `dr:<deal_id>:pe` и `dr:<deal_id>:np`. Связь сделки с сообщением сохраняется в Redis-хеш `dispute_tg_msg:<deal_id>` на 7 дней.
5. Провайдер нажимает "Есть платёж". Бот получает нажатие через long polling и сначала сверяет чат: нажатие принимается, только если оно пришло из того же чата, куда ушла карточка. `callback_data` формирует клиент, поэтому `deal_id` из кнопки сам по себе не доказывает, что чат владеет сделкой, и на чужое нажатие бот отвечает "Кнопка не относится к этому чату". Затем он берёт замок `SET NX dispute_tg_lock:<deal_id>` на 2 минуты, чтобы два быстрых нажатия не ушли в core дважды.
6. Сервис отправляет `Payments.Dispute.TGRespond` с `deal_id`, `action`, `responder_username`, `group_id` и `correct_amount`. На ошибку он повторяет вызов с паузами 0, 200, 500 мс и 1 с, всё в пределах 10 секунд. Когда core принял ответ, карточка теряет кнопки и получает строку "Диспут подтвержден (@username)" или, для кодов `np` и `rj`, "Диспут отменен (@username)" со временем закрытия по Москве. Если у нажавшего нет username, в строку попадают его имя и фамилия. В Redis ставится `responded = 1`.
7. Если спор закрыли в админке, кнопку никто не нажмёт. Для этого раз в 30 секунд сервис обходит все карточки без ответа и спрашивает у core `Payments.Deal.GetStatus`. Статус уже не `DISPUTE` - карточка закрывается от имени "Администратор": "подтвержден" для `COMPLETED`, "отменен" для остальных.

## Из чего состоит сервис

У сервиса два входа: события из NATS и нажатия из Telegram. Оба сходятся в usecase, а наружу сервис ходит через Redis, CQRS-клиенты и того же бота.

![Компоненты telegram.service.go: controller/nats_rpc принимает события от core и rate.service.go и раздаёт их usecase/dispute, usecase/bind и usecase/tech_alert; все три отправляют сообщения через controller/tgbot, который говорит с Telegram Bot API и передаёт нажатия обратно в usecase/dispute; usecase/dispute хранит карточки в repo/redis и вызывает core и files.service.go через repo/webapi](docs/diagrams/c4-components.svg)

`controller/tgbot` одновременно и вход, и выход: он опрашивает Telegram и отправляет туда карточки от имени usecase. Use case ответа подключается к боту уже после старта CQRS-клиента (`SetRespondUseCase`, `internal/app/app.go`). Сверка раз в 30 секунд - отдельная горутина из того же `usecase/dispute` (`reconciler.go`). Если usecase вернул ошибку, `controller/nats_rpc` пишет её в лог с `deal_id`: события golang-cqrs без JetStream не повторяются.

## Какая кнопка что значит

Набор кнопок зависит от причины спора и направления сделки (`controller/tgbot/formatter.go`). core переводит код действия в решение по спору (`core.service.go/internal/delivery/cqrs/dispute_tg_respond.go`):

| Причина и направление | Кнопки | Код -> решение в core |
|---|---|---|
| `PAYMENT_EXISTS` | "Есть платёж" / "Нет платежа" | `pe` -> `RESOLVED` / `np` -> `REJECTED` |
| `NO_PAYMENT`, `IN` | "Есть платёж" / "Нет платежа" | `rj` -> `REJECTED` / `pe` -> `RESOLVED` |
| `WRONG_AMOUNT`, `IN` | "Подтвердить сумму" / "Отклонить" | `ca` -> `AMOUNT_CHANGED` / `rj` -> `REJECTED` |
| `NO_PAYMENT` или `WRONG_AMOUNT`, `OUT` | "Оплачено" / "Оспорить" | `op` / `od` - ручная проверка |

Во второй строке одинаковые подписи дают противоположные коды: код описывает исход спора, а не факт платежа. Если мерчант пишет "платежа нет", а провайдер отвечает "есть платёж", спор отклоняется, и сделка остаётся `COMPLETED`.

Для выплат ответ провайдера спор не закрывает. Заголовок карточки меняется на "Ручная проверка", а вместо времени закрытия появляется упоминание саппорта из `support_mention`.

## Почему состояние живёт в Redis

Всё, что сервис помнит о карточке, - это чат, номер сообщения, исходный текст и флаг ответа. Эти данные нужны, пока спор открыт, поэтому мы храним их в Redis-хеше `dispute_tg_msg:<deal_id>` с TTL 7 дней и обходимся без своей базы. Рядом лежат упоминание саппорта и исправленная сумма для `WRONG_AMOUNT`, которую сервис передаёт в `TGRespond` как `correct_amount`.

За это приходится платить. Если ключ истёк или Redis потерял данные, нажатие кнопки вернёт провайдеру "Не удалось обработать ответ", и спор придётся закрывать в админке. Сверка раз в 30 секунд тоже опирается на Redis: `SCAN dispute_tg_msg:*` и по одному `Payments.Deal.GetStatus` на каждую открытую карточку.

## Что ещё умеет бот

Когда бота добавляют в группу, он отвечает сообщением с ID чата (`my_chat_member` в `client.go`). Этот ID оператор вносит в карточку провайдера. После привязки core публикует `Providers.TGBot.Bound`, и бот пишет в группу "Бот успешно привязан к платформе". Саму привязку делает core, сервис только сообщает о ней.

Технический алерт `System.TechAlert` с полями `service`, `severity`, `title`, `message` и `trace_id` уходит в группу `TECH_ALERTS_TG_GROUP_ID`. Отправляет его отдельный бот с токеном `TECH_ALERTS_BOT_TOKEN`, а если токен пуст - основной. Алерт может прислать любой сервис, поэтому все поля экранируются перед HTML-разметкой: угловая скобка в тексте ошибки не сломает сообщение. Такие алерты публикует rate.service.go.

## Что сервис принимает и вызывает

| Имя | Тип | Другая сторона |
|---|---|---|
| `Payments.Deal.Disputed` | событие, вход | core, `infrastructure/services/telegram/publisher.go` |
| `Providers.TGBot.Bound` | событие, вход | core, `infrastructure/services/telegram/bind_publisher.go` |
| `System.TechAlert` | событие, вход | rate.service.go |
| `Files.GetURL` | запрос, выход | files.service.go, приложение `CQRS_FILES_APP` |
| `Payments.Deal.GetStatus` | запрос, выход | core worker, приложение `CQRS_PAYMENTS_APP` |
| `Payments.Dispute.TGRespond` | команда, выход | core worker, приложение `CQRS_PAYMENTS_APP` |

Если отправить карточку не удалось, сервис пишет ошибку в лог и увеличивает счётчик ошибок. Событие не повторяется: спор остаётся в админке, где его можно закрыть вручную. HTTP-сервер поднимается после подключения к NATS и на `HTTP_PORT` отдаёт `GET /healthz`, `GET /readyz` и счётчики expvar на `GET /debug/vars`: отправленные карточки, ошибки, дубли нажатий, повторы `TGRespond`.

## Конфигурация

Обязательна только `TELEGRAM_BOT_TOKEN`. Остальное - с дефолтами из `config/config.go`:

| Переменная | По умолчанию | Что задаёт |
|---|---|---|
| `TECH_ALERTS_BOT_TOKEN` | пусто | отдельный бот для алертов; пусто - алерты шлёт основной |
| `TECH_ALERTS_TG_GROUP_ID` | `0` | группа для алертов; `0` - алерты не отправляются |
| `REDIS_URL` | `redis://localhost:6379` | карточки и замки |
| `CQRS_TRANSPORT`, `CQRS_NAMESPACE` | `nats://localhost:4222`, `pay` | NATS и namespace golang-cqrs |
| `CQRS_APP_NAME` | `telegram-service` | имя сервиса в discovery |
| `CQRS_PAYMENTS_APP` | `payments-core` | имя процесса `worker` из core, которому адресованы `TGRespond` и `GetStatus` |
| `CQRS_FILES_APP` | `files-service` | имя приложения files.service.go |
| `CQRS_WORKERS_POOL_SIZE` | `10` | обработчики входящих событий |
| `HTTP_PORT` | `:8091` | health и `/debug/vars` |

golang-cqrs ищет получателя по точному имени приложения. `CQRS_PAYMENTS_APP` должен совпадать с `APP_NAME` процесса `worker` из core, где зарегистрированы обработчики: в Helm это `payments-core`, дефолт совпадает с ним, а в docker-compose процесс называется `worker`. Если в рабочей директории есть `.env`, конфиг читается из него, и значения из файла перекрывают одноимённые переменные окружения.

## Как запустить и проверить

Здесь только документация и схемы: исходный код и стек запуска остаются в приватном репозитории. Юнит-тесты покрывают usecase спора (отправка, ответ, проверка чата, строки статуса, сверка), форматирование карточек и алертов и Redis-репозиторий на miniredis; CQRS-клиенты проверяются на настоящем NATS отдельным тегом `integration`.

## Что стоит знать заранее

Вложение Telegram скачивает сам по presigned-ссылке, поэтому хранилище файлов должно быть доступно из интернета.

Запускать можно только одну реплику: long polling с одним токеном не делится между процессами.
